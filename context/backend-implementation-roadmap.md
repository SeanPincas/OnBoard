# OnBoard backend implementation roadmap

Status: Phase 1 in progress. The shared application scaffold, initial dependencies, Supabase CLI configuration, environment template, and process-liveness endpoint have been introduced. Feature APIs, schema, and hosted integrations are not implemented yet. See [service setup](service-setup-checklist.md) and [actual API contracts](backend-api-contracts.md).

The [project README](../README.md) defines the agreed product scope. This document turns that scope into ordered backend work. The [frontend implementation guide for Claude Code](frontend-implementation-guide.md) defines the separate UI roadmap and integration matrix; this document does not select visual designs or implement screens.

## Architecture and boundaries

- **Next.js App Router + TypeScript:** application server routes and server-side business logic live in `frontend/` alongside the application. Backend work includes these routes even though their physical location is in `frontend/`.
- **Supabase PostgreSQL + PostGIS:** persistent application data, geographic search, constraints, transactions, and access policies.
- **Supabase Storage:** listing images.
- **Supabase Realtime:** authenticated conversation updates; PostgreSQL remains the message source of truth.
- **Clerk:** registered-user identity, sessions, and email verification. Brevo is not required for authentication.
- **Guest sessions:** application-managed demo access without a Clerk account, isolated per visitor.
- **MapLibre:** frontend map rendering. Backend work supplies coordinates, radius-search results, and any address-search integration; map tiles and geocoding are separate provider decisions.

Keep migrations, database functions, seeds, and database checks under `backend/`. Keep reusable server services separate from route handlers so validation, permissions, and business rules are not duplicated.

## Dependencies and installation plan

This is an installation checklist; inspect package manifests/lockfiles for actual installed versions. npm is used for the initial setup. Commit generated lockfiles and resolve compatible package versions during setup.

### Machine prerequisites

| Prerequisite | Purpose | Needed by |
| --- | --- | --- |
| Supported Node.js LTS and npm | Run Next.js, package installation, and development tools; verify compatibility with the selected Next.js, Clerk, Supabase CLI, and Vitest versions | Phase 1 |
| Git | Track source, migrations, and lockfiles | Phase 1 |
| Docker Desktop or a Docker-compatible runtime | Run the local Supabase stack; on Windows, configure its supported virtualization/WSL setup as needed | Phases 1–2 |
| Clerk development application | Configure and verify real authentication and verification emails | Phase 3 |
| Supabase project | Verify hosted database, Clerk integration, Storage, and Realtime behavior | Hosted integration and deployment |

Node.js and Docker are machine installations, not npm dependencies. Local Supabase can be developed before a hosted Supabase project is configured. Account credentials belong in ignored local environment files, never in this document or committed source.

### Application packages — `frontend/`

Next.js hosts the server routes, so backend runtime packages belong in the application package rather than in a duplicate backend web server.

| Package | Type | Purpose | Install timing |
| --- | --- | --- | --- |
| `next`, `react`, `react-dom` | Runtime | Application framework and route-handler host | Phase 1, through the Next.js scaffold |
| `typescript`, `@types/node`, `@types/react`, `@types/react-dom` | Development | Type checking and runtime/framework type definitions | Phase 1, through the scaffold |
| `eslint`, `eslint-config-next` | Development | Static checks for the Next.js application | Phase 1, through the scaffold |
| Tailwind tooling generated by the scaffold | Development/build | Shared frontend styling foundation; retain the generated compatible configuration | Phase 1, through the scaffold |
| `@clerk/nextjs` | Runtime | Clerk server/session helpers and frontend auth integration | Phase 3 |
| `@supabase/supabase-js` | Runtime | Database queries, database function calls, Storage, and Realtime clients | Phase 2 onward |
| `zod` | Runtime | Request, environment, and onboarding validation with inferred TypeScript types | Phase 1 onward |
| `vitest` | Development | Focused service, validation, permission-integration, and concurrency checks | Introduce with the first relevant checks |

Create the application once from the **OnBoard root**, while `frontend/` is still empty:

```powershell
npx create-next-app@latest frontend --typescript --tailwind --eslint --app --src-dir --use-npm
```

If the frontend already has an application by implementation time, reuse it instead. Do not scaffold over existing work.

After scaffolding, run these from **`frontend/`**, installing packages when their phase needs them:

```powershell
npm install @supabase/supabase-js zod
npm install @clerk/nextjs
npm install --save-dev vitest
```

Configure Vitest and test scripts as part of implementation; installing the package alone does not create working checks. SQL permission/constraint checks also need the local database and appropriate database test tooling.

Official references: [Next.js installation](https://nextjs.org/docs/app/getting-started/installation), [Clerk Next.js quickstart](https://clerk.com/docs/nextjs/getting-started/quickstart), [Supabase JavaScript installation](https://supabase.com/docs/reference/javascript/installing), [Zod installation](https://zod.dev/), and [Vitest setup](https://vitest.dev/guide/).

### Database tooling — `backend/`

Use a small tooling-only npm package in `backend/` for the Supabase CLI. This does not create another HTTP server. Run from **`backend/`** during Phase 1:

```powershell
npm init -y
npm install --save-dev supabase
npx supabase init
```

This produces `backend/supabase/` for configuration, migrations, seeds, and database tests. Once Docker is installed and running, start the local stack from **`backend/`**:

```powershell
npx supabase start
```

Use the project-local CLI through `npx`; do not use `npm install -g supabase`. Document the resulting local connection settings and development commands without committing secrets. See [Supabase local development](https://supabase.com/docs/guides/local-development).

### Database extensions and managed services

- **PostGIS:** enable in a version-controlled database migration during Phase 2. It is a PostgreSQL extension, not an npm package. See [Supabase PostGIS](https://supabase.com/docs/guides/database/extensions/postgis).
- **Supabase Storage and Realtime:** configure the services and their policies; use the existing `@supabase/supabase-js` client rather than installing separate storage/chat SDKs.
- **Clerk email verification:** configure in Clerk; no Brevo package is required.
- **Guest sessions:** initially use server-side cookie APIs, Node.js cryptographic primitives, and the application database. Add a session library only if the implemented design requires it.
- **Reservation transactions:** implement in PostgreSQL functions invoked through the Supabase client; separate JavaScript calls do not form one database transaction.

### Deferred or unnecessary initial dependencies

- `maplibre-gl` belongs to frontend map implementation and will be covered by the separate frontend roadmap.
- Map-tile/geocoding provider packages remain undecided; a provider may work through built-in `fetch` without another SDK.
- Express, a separate Socket.IO server, Prisma/Drizzle, and a direct PostgreSQL Node driver are not required by the current architecture. Add one only for a concrete requirement.
- `@supabase/ssr` is not part of the baseline because Clerk manages authentication sessions. Revisit only if an implementation requirement calls for it.
- A seed-generation library or TypeScript script runner is optional; SQL fixtures and deterministic generators can start without one.
- Browser end-to-end tooling will be coordinated with the frontend roadmap rather than installed in duplicate.

## How to work through this roadmap with Codex

Implement one sub-phase or coherent feature slice at a time. At the start, read the README, this roadmap, applicable repository instructions, and existing implementation. Before provider-specific integration, verify the current official documentation and installed SDK versions.

For each completed slice:

1. Implement the schema, permissions, server behavior, and relevant checks together.
2. Run meaningful validation for the changed behavior.
3. Record completion, affected files, checks run, and any unresolved dependency here.
4. Update API contracts when behavior changes so the frontend roadmap can depend on them.

Codex is especially useful for schema design, SQL migrations, TypeScript services, request validation, access policies, deterministic seed generators, API documentation, and regression checks. Service-account ownership, credentials, billing choices, and final product policy decisions require user input or access. Do not treat a missing external credential as evidence that a live integration passed; continue independent local work and record the limitation.

## Phase 1 — Foundation and contracts

### 1.1 Repository and local setup

- [ ] Establish package management and the minimal Next.js server scaffold needed for API work; coordinate with the future frontend scaffold rather than creating a second app.
- [ ] Set up the local database workflow and version-controlled Supabase migrations under `backend/`.
- [ ] Add environment-variable examples with placeholders and ignore local secrets. Distinguish browser-safe configuration from server-only secrets.
- [ ] Document prerequisites, setup, migration, reset, and seed commands. Reset commands must target the local development database by default.

### 1.2 Domain rules and API contracts

- [ ] Define IDs, pagination, sorting, validation errors, authorization errors, and conflict responses consistently.
- [ ] Document request/response shapes for profiles, onboarding, listings, search, reservations, conversations, and guest sessions.
- [ ] Represent PHP amounts with exact decimal values or integer centavos; avoid floating-point money calculations. Use timezone-aware timestamps and explicit date-only values where appropriate.
- [ ] Define field privacy: public listing data, owner-only management data, and private tenant/account information.

**Done when:** the local setup is reproducible and the initial contracts give frontend work stable mockable interfaces.

**Codex is good at:** scaffolding, typed contracts, validation schemas, and setup documentation. **External dependency:** service projects and credentials are needed for later live integration, not for writing the contracts.

## Phase 2 — Database model and access foundation

### 2.1 Core schema

- [ ] Create profiles linked to Clerk user IDs, private profile details, roles, preferences, and onboarding progress/completion.
- [ ] Create properties, rooms, optional bed spaces, photo metadata, amenities, house rules, and occupancy restrictions.
- [ ] Separate draft/published/archived publication state from physical availability.
- [ ] Model whole-room versus per-bed rental explicitly. Prevent a room and its beds from being offered as conflicting inventory at the same time.
- [ ] Create reservation requests, inventory allocations/occupancies, viewing requests, conversations, participants, and messages.
- [ ] Include demo-session ownership in the schema design before implementing demo mutations; do not add isolation as an afterthought.

### 2.2 Constraints and read models

- [ ] Add foreign keys, capacity and price checks, required coordinate checks, indexes, and valid status transitions where enforceable.
- [ ] Derive available counts from inventory and active allocations rather than maintaining unrelated editable counters.
- [ ] Define safe public listing views or response projections that omit private profile and tenant information.

### 2.3 Access policies

- [ ] Build an actor/resource permission matrix: public viewer, tenant, owning landlord, unrelated landlord, and guest demo actor.
- [ ] Apply row-level security and explicit grants to exposed tables, storage objects, and relevant database functions.
- [ ] Ensure sensitive database functions cannot bypass permissions through caller-supplied owner IDs or an unsafe execution context.
- [ ] Add focused checks proving owners can manage their records and unrelated users cannot read private data or mutate those records.

**Done when:** migrations build a fresh database successfully, invalid inventory is rejected, and access checks cover both allowed and denied operations.

**Codex is good at:** relational modeling, migration SQL, policy implementation, and finding inconsistent inventory rules.

## Phase 3 — Clerk, profiles, and first-time onboarding

### 3.1 Authentication integration

- [ ] Configure Clerk email verification and its supported Supabase third-party authentication integration.
- [ ] Validate identity on the server and propagate verified Clerk identity to database access; never accept a browser-supplied user ID as proof of identity.
- [ ] Provision an application profile idempotently after authentication. If webhooks are used, verify signatures, handle retries, and reconcile out-of-order events.
- [ ] Define account deletion/deactivation handling so retained reservations and conversations remain consistent.

### 3.2 Onboarding persistence

- [ ] Implement read/save/complete operations for role selection, basic profile, and role-specific setup.
- [ ] Save partial progress; validate completion on the server and resume unfinished onboarding.
- [ ] Persist tenant budget, preferred city, room/bed preference, occupancy, move-in date, and optional destination/radius.
- [ ] Persist landlord profile and primary city without requiring a published listing.
- [ ] Keep role changes controlled by the server. Completing an arbitrary browser form must not authorize edits to another landlord's property.

**Done when:** a new registered user can save, resume, and finish onboarding; a returning completed user is recognized; private fields stay private.

**Codex is good at:** integration code, profile synchronization, validation, and authorization checks. **External dependency:** Clerk/Supabase configuration and test credentials are required to verify real sign-in and email delivery.

## Phase 4 — Isolated Guest demo sessions

### 4.1 Guest identity and isolation

- [ ] Finalize session expiry, persistence, reset, and cleanup rules. Recommended approach: an opaque, server-issued cookie references a database-backed demo session, with template data copied into a session-owned workspace.
- [ ] Resolve tenant and landlord demo identities on the server within the same session. Role switching changes the active demo actor only.
- [ ] Keep template seed records immutable to guests. Scope every guest write and private read to its session workspace.
- [ ] If privileged database access is necessary for guest routes, centralize it behind server-only functions with explicit session scoping. Never expose privileged keys or allow guests to choose arbitrary session/owner IDs.

### 4.2 Guest feature access

- [ ] Implement guest entry, current-session lookup, role switching, reset, expiry, and scoped cleanup.
- [ ] Support the same domain workflows through shared business services with registered or demo actor context.
- [ ] Set demo operation/upload limits and protect cookie-authenticated mutations against cross-site requests.
- [ ] Define demo chat transport explicitly: without a verified Realtime identity/policy path, deliver guest message updates through session-checked server polling initially. Do not expose private Realtime channels publicly.

**Done when:** two independent visitors can explore and modify their own demo data without changing each other's data, registered users' data, or seed templates; expired/reset sessions lose access.

**Codex is good at:** session services, template cloning, scoped queries, and cross-session isolation checks. **Product decision:** approve the exact expiry/reset behavior before treating it as final.

## Phase 5 — Landlord inventory and listing images

### 5.1 Property and inventory management

- [ ] Implement owner-scoped create/read/update/archive operations for properties, rooms, and bed spaces.
- [ ] Support price basis, move-in cost components, amenities, rules, occupancy restrictions, and available-from dates.
- [ ] Validate publication requirements, including 4–6 listing images, address, coordinates, rent, and capacity. Allow incomplete drafts.
- [ ] Prevent destructive inventory edits that invalidate active reservations or occupied units; archive or require a defined transition instead.

### 5.2 Image lifecycle

- [ ] Configure storage paths and policies for owner/session isolation, with published images readable as intended.
- [ ] Validate file type, size, image count, ordering, and ownership; set safe limits and handle failed uploads.
- [ ] Distinguish staged uploads from attached images and clean up abandoned objects safely.
- [ ] Ensure guest resets never delete another visitor's files or shared seed images.

**Done when:** an owning landlord can publish and update a valid listing, another landlord cannot edit it, and image upload/removal respects ownership and limits.

**Codex is good at:** CRUD services, validation, storage policy code, and failure handling. **External dependency:** a configured bucket is needed for end-to-end upload verification.

## Phase 6 — Feed, filters, and geographic search

### 6.1 Listing discovery

- [ ] Implement paginated published listing reads with stable sorting and summary/detail projections.
- [ ] Filter by city/address text, budget, room/bed type, amenities, occupancy restrictions, available-from date, and availability.
- [ ] Show monthly price basis, move-in cost, and remaining inventory consistently. Keep full properties queryable through an explicit include-unavailable option.

### 6.2 Radius search

- [ ] Store geographic points and add spatial indexes.
- [ ] Implement meter-based radius queries using PostGIS with validated coordinates and bounded radius values.
- [ ] Return distance and coordinates; use the same filters for feed and map results. Bound map results and clearly indicate truncation or pagination.
- [ ] Check center-point matches, inside/outside/boundary cases, coordinate order, empty results, and separation of Manila City from Cebu City.

### 6.3 Address and landmark lookup

- [ ] Define a provider-independent geocoding contract and local seeded landmark lookup so development can proceed before a provider is chosen.
- [ ] After provider selection, implement required attribution, caching/usage rules, request limits, and provider-error handling according to its current terms.
- [ ] Support manual pin placement when address lookup fails.

**Done when:** feed and map queries agree on availability and radius membership and return only public data.

**Codex is good at:** query design, indexing, geospatial SQL, pagination, and deterministic distance checks. **External decision:** map tiles and geocoding provider; no paid subscription is assumed.

## Phase 7 — Viewing requests, reservations, and occupancy

### 7.1 Request lifecycle

- [ ] Define a transition table with allowed actors for pending, confirmed, declined, cancelled, and any agreed expiry states. Keep request status separate from inventory/occupancy status.
- [ ] Implement viewing requests and reservation submission, owner review, tenant cancellation, and move-in handling.
- [ ] Store requested occupants, intended move-in date, agreed price snapshot, and the exact requested inventory.
- [ ] Validate capacity and disclosed accommodation restrictions without silently guessing a person's gender from their name.
- [ ] Settle cancellation, confirmation expiry, and move-out rules before enabling their corresponding transitions; avoid introducing automatic expiry without an agreed policy.

### 7.2 Concurrency and availability

- [ ] Confirm reservations in a single database transaction with appropriate locking/constraints and a fresh availability check.
- [ ] Make retries safe: duplicate submissions or repeated confirmation must not allocate twice.
- [ ] Keep pending requests from consuming inventory; confirmed reservations consume it, and move-in changes the allocation to occupied.
- [ ] Release inventory only through authorized, valid transitions. Return clear conflicts when another request wins.
- [ ] Check two simultaneous confirmations for the last slot, multi-occupant capacity, separate beds in the same room, cancellation, and retry behavior.

**Done when:** reservation requests follow the agreed flow, simultaneous requests cannot overbook inventory, and full/available counts remain correct after each transition.

**Codex is good at:** state machines, transactions, concurrency checks, and edge-case analysis. **Product dependency:** final cancellation/expiry/move-out policy.

## Phase 8 — Conversations and live updates

### 8.1 Persistent chat

- [ ] Create conversations tied to a property/room and the participating tenant and landlord.
- [ ] Implement participant-only conversation lists, paginated history, and message sending with size/rate limits.
- [ ] Prevent duplicate conversations where reuse is intended and make send retries safe.
- [ ] Persist messages before acknowledging success. Use plain text initially and render safely in the frontend.
- [ ] Connect viewing/reservation actions to the relevant conversation without exposing other tenants' private requests.

### 8.2 Realtime delivery

- [ ] Configure authenticated, participant-authorized Realtime delivery using the selected supported mechanism.
- [ ] Handle reconnects through persisted message history and stable IDs; deduplicate repeated updates.
- [ ] Apply the guest transport established in Phase 4 and verify cross-session privacy separately.

**Done when:** two authorized participants exchange persistent messages, reconnect without losing history, and an unrelated actor cannot read or subscribe to their conversation.

**Codex is good at:** message APIs, subscription integration, retry handling, and permission checks. **External dependency:** configured Realtime service for live delivery verification.

## Phase 9 — Complete Manila City and Cebu City demo dataset

Introduce a small deterministic fixture as early as Phase 2 for development; expand it here once the workflows stabilize.

### 9.1 Seed design

- [ ] Choose balanced dataset counts and neighborhoods for each city; clearly distinguish Manila City from all of Metro Manila and Cebu City from the wider province.
- [ ] Generate reproducible fictional profiles, property descriptions, plausible coordinates, PHP prices, rules, and gender restrictions.
- [ ] Cover single-room properties, multi-room buildings, bed spaces, partially occupied properties, reserved units, and full properties.
- [ ] Seed consistent viewing requests, reservations, occupancies, and sample conversations, including a useful initial state for both guest roles.
- [ ] Use seeded landmarks to demonstrate a radius with matches and one without matches.

### 9.2 Image assets and repeatability

- [ ] Prepare 4–6 suitable images per listing, matching room descriptions and marked as demo imagery. Generated assets can be added as a separate image-generation task.
- [ ] Keep asset manifests and provenance references. Do not present fictional listings as real vacancies.
- [ ] Make seed/template initialization repeatable, with stable IDs and a safe reset process limited to development/demo targets.
- [ ] Check seed referential integrity, availability totals, asset paths, and geographic coverage.

**Done when:** a clean setup produces a believable, consistent two-city demo and each guest session starts from that same known baseline.

**Codex is good at:** deterministic data generators, fixtures, manifests, and consistency checks. **User review helps with:** local plausibility, imagery, and presentation quality.

- [ ] Verify registered onboarding, landlord publication, tenant radius search, viewing/reservation flow, chat, and Guest entry/role switching/reset end to end.
- [ ] Re-run the critical permission, guest-isolation, storage-access, and last-slot concurrency checks.
- [ ] Inspect representative query plans and remove avoidable unbounded queries or repeated queries on feed/detail pages.

### 10.2 Deployment preparation

- [ ] Choose hosting and record required environment variables, database migrations, Clerk configuration, webhook URLs if used, storage, and Realtime configuration.
- [ ] Add useful server error logs without private profile data, secrets, or verification codes.
- [ ] Document demo cleanup scheduling, migration recovery, and backup/restore options appropriate to the chosen service plans.
- [ ] Prepare a deployment checklist and smoke-check script. Verify against the selected hosting/service limits rather than assuming free tiers cover every feature.

### 10.3 Frontend handoff

- [ ] Document implemented operations, response examples, validation, statuses, pagination, guest transport, and auth/onboarding behavior.
- [ ] Export reusable TypeScript types where practical and supply stable seed IDs for frontend integration.
- [ ] Record completed phases and outstanding external configuration or product decisions honestly.

**Done when:** the backend supports the agreed demo workflows, critical checks pass, and the frontend can integrate through documented contracts. Deployment readiness is distinct from an actual verified deployment.

**Codex is good at:** integration debugging, focused regression coverage, API documentation, and deployment preparation. **External dependencies:** hosting/service access and any selected plan configuration.

## Scope limits and unresolved decisions

Payments, public reviews, formal identity verification, video reels, and route-based travel distances remain outside the initial build.

Resolve these at the relevant phase rather than blocking all implementation:

- Guest expiry, reset, persistence, and cleanup behavior: Phase 4.
- Map tiles and geocoding provider: Phase 6.
- Cancellation, reservation expiry, and move-out rules: Phase 7.
- Exact seed counts, neighborhoods, and image set: Phase 9.
- Hosting, service plans, and deployment configuration: Phase 10.
